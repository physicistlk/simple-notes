## Findings

### P1 — functional / correctness

1. **Continuous mode is still blurry when pinched.** `ContinuousPageView` renders every vector page at a fixed `targetW = 1600` (`CanvasScreen.kt:3301`) and the zoom is a `graphicsLayer` upscale of that bitmap. This is exactly the reported "pinch out → pixelated" defect, still unfixed in continuous mode. Needs the render width driven by the zoom scale (re-render with hysteresis, area-capped).
2. **Continuous zoom does not change list layout.** The `graphicsLayer` scale is applied to the whole overlay, not to item sizes. Compose hit-testing follows the layer transform, so taps land, but scroll extent does not grow with the zoom: after zooming in, off-screen parts can only be reached by dragging, and the pan offsets accumulate outside the list's scroll bounds.
3. **Bitmap recycling in composition.** `ContinuousPageView` recycles its bitmap in `onDispose` (`:3274`) and before replacing state (`:3331`). `Image(bitmap.asImageBitmap())` wraps the same `Bitmap` on API 29+, and a still-pending draw can hit a recycled bitmap (`Canvas: trying to use a recycled bitmap`). Prefer letting GC collect, or recycle only from an explicit cache eviction path.
4. **PDF opened on the main thread during composition.** `remember { pdfDocCache.document(...) }` (`:3280`) reads and parses the PDF synchronously; the first composition of a page in a large PDF can jank/ANR. Move it to `produceState`/IO with a placeholder ratio.
5. **Continuous scrolling loads pages into the hidden canvas.** `setCurrentPageIndex` on scroll (`:1216`) fires `LaunchedEffect(currentPageIndex)` (`:352`), which decodes and applies every scrolled page to the hidden `DrawingCanvasView`. Gate that effect on `!isContinuous` and apply only when switching to single mode.

### P2 — memory / OOM

6. **PDF render budget is now 72 MB per background.** `PdfRenderPolicy.MAX_PIXELS = 18_000_000` (72 MB ARGB) and a re-render keeps old + new alive (144 MB). With 6 undo snapshots of a 2160×3056 page (26 MB each ≈ 158 MB) this sits close to the `largeHeap` ceiling; a 256 MB-heap minSdk-21 device will OOM. Suggest 8–12 MPx, hysteresis 1.25–1.35, and/or downscaled undo snapshots.
7. **Overflow layer can be 4096×4096 (67 MB).** `initBackingBitmap` caps both sides at 4096 (`DrawingCanvasView.kt:814-815`), so a 2160×3056 PDF page asks for 4096×4096. Size it relative to the page, not the global cap.
8. **Continuous page bitmaps are heavy for their quality.** ~14.5 MB per 1600-px page, several composed at once. Since 1600 px is not enough for zoom anyway, render at viewport width × zoom with an area cap.

### P3 — data integrity

9. **Backup/restore now carries `-shm`.** The WAL is checkpointed before backup (good), but restoring `touchnotes.db-shm` is unnecessary and can be inconsistent with the restored db; restore `db` + `-wal` only and delete `-shm`. Also consider an integrity/version check after restore.
10. **Debounced save can race a recycled bitmap.** `saveCurrentPageBitmapDirect` does not check `isRecycled`; undo/page switches recycle the backing bitmap. `BitmapUtils.saveBitmapToPng` catches the exception, so the failure is silent (lost stroke) rather than a crash. A defensive copy or `isRecycled` guard closes the race.

### P4 — minor

11. `PdfRenderPolicy.capPxPerPt` KDoc still cites the old 8 MPx budget.
12. `PageTurningSettingsTest` asserts implementation constants (18 MPx, 1.15); behaviour-based assertions age better.
13. PDFs imported before the vector engine (`pdfSourcePath = ""`) remain raster forever — re-import is still the only fix.
14. `state/STATE.md` / `FEATURES.md` do not describe the six commits yet.
15. Six commits are local only (`origin/main` is at `2676e7b`).

## Resolution — P1 fixes

All five P1 findings are addressed:

1. **Zoom-aware continuous rendering.** `ContinuousPageView` now measures its
   laid-out width (`BoxWithConstraints`), multiplies it by a quantised zoom
   bucket (1 / 1.5 / 2 / 3), and asks `PdfRenderPolicy.continuousRenderWidth`
   for a render width capped at 12 MPx (~2900 px on A4) and 4096 px. The page
   is rendered with `PdfiumDocument.renderPageInto` directly into the output
   bitmap (single allocation) and the stroke layer is drawn on top.
2. **Zoom/scroll consistency.** The Lazy list keeps ownership of scrolling, and
   the `graphicsLayer` translation is clamped to `[-viewport·(scale−1), 0]` on
   both axes, so a zoomed page can never be pushed out of view; offsets reset
   when the scale returns to 1.
3. **No recycling from composition.** `ContinuousPageView` no longer recycles
   bitmaps in `onDispose` or on state replacement; the GC reclaims them once the
   composable drops its reference. The old bitmap stays on screen while a new
   zoom bucket renders, so pinching does not flash a placeholder.
4. **PDF work off the main thread.** Page aspect ratio is read in
   `produceState` on `Dispatchers.IO`; rendering happens on IO too, after an
   80 ms settle delay so intermediate pinch buckets are cancelled before a
   full-page allocation (pdfium renders are not cancellable).
5. **No page loading while reading.** The page-change effect is keyed on
   `pageTurningMode` and returns early in continuous mode, so scrolling no
   longer decodes each page into the hidden canvas; switching to single page
   still loads the target page.

## Resolution — P2 and P3

6. **Heap-aware PDF budget.** `DrawingCanvasView` now derives `pdfPixelBudget`
   from `Runtime.maxMemory() / 24`, clamped to 4–18 MPx, and passes it to
   `PdfRenderPolicy.capPxPerPt(maxPixels = …)`. A large-heap tablet keeps the
   18 MPx ceiling; a 256 MB device gets roughly half, keeping old + new
   bitmaps for one re-render inside the heap.
7. **Dead overflow layer removed.** `overflowBitmap` was allocated (up to
   4096×4096 ≈ 67 MB) but nothing ever drew into it, and it stayed allocated
   for the whole session. The field, its allocation in `initBackingBitmap`,
   its draw in `onDraw`, and its clear in `clearCanvas` are gone.
8. **Continuous page budget** (also P1): `CONTINUOUS_MAX_PIXELS = 12 MPx`,
   `PdfiumDocument.renderPageInto` composites PDF + strokes into a single
   allocation, and pages are rendered at viewport width × quantised zoom.

9. **Backup no longer archives or restores `-shm`.** The shared-memory index
   is derived state; SQLite rebuilds it on open. Archives contain `db` +
   `-wal` only.
10. **Debounced-save self-cancel fixed.** `scheduleDebouncedSave`'s coroutine
    *was* the pending job, and it called `saveCurrentPageBitmapDirect`, which
    cancelled that job — so the write never ran and strokes were silently
    lost. The save body now lives in a private `persistPageBitmap` that does
    not cancel; the public entry points cancel the pending job and then call
    it. `persistPageBitmap` also drops recycled bitmaps defensively.

Related hardening (found while fixing 10): `loadBitmap`, `undo` and `redo` no
longer recycle the backing bitmap they replace, because a debounced save may
still hold it. The GC reclaims it instead; this removes a second silent
stroke-loss path.

11. **Stale KDoc fixed:** `capPxPerPt` no longer cites the old 8 MPx figure.
12. Left as-is: the policy tests still pin the 18 MPx / 1.15 constants. They
    are cheap regression anchors; behaviour tests for the new helpers were
    added alongside.

## Continuous-reading correctness pass (follow-up)

Found while reviewing the P1/P2/P3 work:

16. **Saves were filed under the wrong page in continuous mode.**
    `_currentPageIndex` follows the scrolled page, but the drawing canvas
    behind the reader keeps whatever page was loaded into it. Leaving the note
    (`saveAndExit`) therefore wrote the hidden canvas's page (usually page 1)
    over the page the reader had scrolled to, destroying that page's strokes.
    Fixed by adding `CanvasViewModel.canvasPageIndex` — "the page whose content
    the canvas holds" — set at every apply point (factory load, page-change
    effect, `goToPage`, `addNewPage`, `deletePage`). All three save entry
    points now default their page index to it instead of to the current page.
17. **Debounced saves could target the next page.** `persistPageBitmap` read
    `_currentPageIndex` at write time, up to 1.5 s after the bitmap was
    captured, so a stroke on page N followed by a fast page flip was written
    to page N+1. The index is now captured at call time (and validated against
    the page count).
18. **Tapping a continuous page decoded it twice and dropped its layers.**
    The tap called `goToPage(forceReload = true)` while the page-change effect
    also fired for `pageTurningMode`; the `goToPage` callback used
    `applyLoadedPage`, which does not restore image layers. The tap now just
    sets the page index and the mode; the effect performs the single load,
    layer restore included.
19. **Flipping the reading direction in continuous mode jumped to page 1.**
    The "scroll to current page" effect was keyed only on `isContinuous`; the
    newly composed Lazy list started at index 0. It is now keyed on
    `isHorizontal` too.

## Leave-save pass

20. **System back, tab close and note switch never wrote the last stroke.**
    The only exit paths that saved were the toolbar back arrow (`saveAndExit`)
    and the 1.5 s debounce. Navigation that disposes the screen cancels
    `viewModelScope`, so a stroke finished less than the debounce window
    before a system-back gesture, a tab close, a note switch or opening the
    text editor was silently lost. `CanvasViewModel.scheduleDebouncedSave`
    now records the pending `(pageIndex, bitmap)` pair; `flushPendingSave` is
    called from a `DisposableEffect` in `CanvasScreen` and writes it on
    `TouchNotesApp.appScope`, which outlives the ViewModel. No extra write
    happens when nothing is pending, so ordinary exits stay cheap.
21. **Internal saves used the scrolled page index.** `goToPage` and
    `addNewPage` saved the canvas bitmap under `_currentPageIndex`, which
    continuous mode had already moved to the scrolled page. They now use
    `canvasPageIndex` like every other save path.

22. **Volume-key page turn did nothing in continuous mode.** It called
    `nextPage`/`previousPage`, which loads a page into the hidden canvas while
    the reader overlay ignores it (and the scroll-sync effect immediately
    reset the index). Volume up/down now move the continuous reader by one
    page and leave the hidden canvas alone.

23. **Layer edits were lost on system back.** Image layers live outside the
    backing bitmap, so only `saveAndExit` (toolbar back) persisted them; a
    system back, tab close or note switch dropped a just-dragged or hidden
    image. `DrawingCanvasView.layersDirty` now tracks unsaved layer edits (set
    by add/delete/reorder/visibility/opacity and by the end of a drag or pinch
    gesture, cleared by `saveImageLayers`/`applyLoadedLayers`), and the screen's
    dispose effect writes them on the application scope when dirty. The
    page-change layer reload is also skipped while dirty, so a page flip can no
    longer revert an unsaved move by re-applying the on-disk copy.

24. **The first vector page of a note was opened on the main thread.**
    `applyPdfBackground` reads the page size of the open pdfium document
    synchronously (it must, so the page rect is installed before the stroke
    layer), and the open parses the whole PDF. The factory load, the
    page-change effect and the post-import apply now call
    `preloadPdfSource` (Dispatchers.IO) first, so the apply is a cache hit;
    navigation callbacks are unaffected because the cache is already warm for
    the note's source. A note holding pages from two different PDFs (import
    appends) can still re-parse once on a flip — acceptable, and rare.

## Library card for vector PDF notes

29. **PDF notes showed an unannotated card.** After F-10 a vector page split
    into a clean `page_<i>.png` render and a transparent `strokes_<i>.png`, but
    the card only read the former, so annotating a PDF never changed its
    library thumbnail (the original shows the writing). The card now composes
    the two for the first page unless the user picked a custom cover, which
    needs no new files, no pdfium call and no change to export: raster pages
    have no strokes file and export still flattens page + strokes itself.
    `BitmapUtils.loadAlphaThumbnail` exists because the existing thumbnail
    loader decodes RGB_565, which would render a transparent ink layer black.

30. **Legacy raster pages cost two full-size allocations each in the reader.**
    `loadPageBitmap` decodes the page PNG and then copies it to ARGB_8888
    (2160×3056 ⇒ ~26 MB decoded + ~26 MB copy), and continuous reading keeps
    several pages alive. `NoteRepository.loadPageBitmapForDisplay` decodes once
    at RGB_565 sized for the displayed width, which is what the read-only
    overview needs; single-page mode still loads the full ARGB bitmap for
    drawing.

## Screen lock / deep sleep investigation (2026-11-08)

Report: "simple notes does not go to deep sleep on screen lock."

Measured on the tablet (Xiaomi Pad 5, Android 16 ROM, wireless adb) with the app
in the foreground and the screen off:

- `dumpsys power` → `Wake Locks: size=0`, `mHoldingWakeLockSuspendBlocker=false`;
  `mWakefulness=Dozing` immediately after the display turns off and `Asleep`
  within 60 s. `dumpsys deviceidle` → `mState=IDLE`.
- `dumpsys alarm` / `dumpsys batterystats --checkin` attribute no alarms,
  wakeups or wake locks to `personal.notes.touch` (uid 10465); `awl,0,0`.
- The app declares no permissions at all (merged manifest: only the
  auto-generated `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`), so it cannot even
  request `WAKE_LOCK`; it has no services, alarms, jobs, sensors, audio or
  network activity.
- The app's CPU time did not advance by a single tick across 20 s of screen-off.

So the app itself holds nothing that blocks suspend. The one power-related
switch it owns is "Keep Screen On", a window flag: forcing the setting on shows
`SCREEN_BRIGHT_WAKE_LOCK 'WindowManager/displayId:0' … ws=WorkSource{10465
personal.notes.touch}` and `mHoldScreenWindow` = the MainActivity window.

31. **"Keep Screen On" was applied from composition and never scoped to the
    lifecycle.** `MainActivity` called `window.addFlags/clearFlags` inside
    `setContent`, so the flag's lifetime was tied to a recomposition, not to
    visibility: it was never explicitly released on pause or on screen-off, and
    a ROM that keeps the last activity's window visible behind a lock-screen
    preview would keep the screen wake lock held with the tablet locked. New
    `util/ScreenAwakeController` holds the flag only while *requested* **and**
    resumed **and** the display is on, releases it on `onPause` and on
    `ACTION_SCREEN_OFF`, and re-applies it on resume / `ACTION_SCREEN_ON`.
    `MainActivity` now drives the flag through it (`LaunchedEffect` for the
    setting, lifecycle callbacks, and a runtime receiver for the screen
    broadcasts). Eight unit tests cover the state machine.
32. **PDF re-render while hidden.** `DrawingCanvasView` cancelled its debounced
    vector render only on detach, so locking the screen right after a zoom could
    still run a full pixel-budget pdfium render into a hidden window. The render
    task is now cancelled in `onWindowVisibilityChanged` while invisible and
    re-armed when the window becomes visible again.

Two device settings on this tablet can produce the reported symptom on their
own and are worth checking before blaming the app: `settings get system
screen_off_timeout` = `2147483647` (Never — the display never times out) and
`settings get global stay_on_while_plugged_in` = `15` (stay awake for AC, USB,
wireless and dock, i.e. the screen never turns off while charging).

Device verification of #31/#32 on the tablet (Xiaomi Pad 5, debug build,
setting forced on/off in a backed-up copy of the Room DB and restored after):

| state | window flags of MainActivity | wake locks |
|---|---|---|
| setting on, foreground | `fl=KEEP_SCREEN_ON …` | `SCREEN_BRIGHT_WAKE_LOCK … ws=WorkSource{10465}` |
| setting on, Home pressed (paused) | `fl=` without `KEEP_SCREEN_ON` | none from the app |
| setting on, foreground again | `fl=KEEP_SCREEN_ON …` | `SCREEN_BRIGHT_WAKE_LOCK …` |
| setting off | `fl=` without `KEEP_SCREEN_ON` | `Wake Locks: size=0` |

Screen-off with the setting on: `mHoldScreenWindow=null` and only the system's
`DOZE_WAKE_LOCK 'dream:doze'` remains, so the app releases the display before
