## Findings

### P1 — functional / correctness

1. **Continuous mode is still blurry when pinched.** `ContinuousPageView` renders every vector page at a fixed `targetW = 1600` (`CanvasScreen.kt:3301`) and the zoom is a `graphicsLayer` upscale of that bitmap. This is exactly the reported "pinch out → pixelated" defect, still unfixed in continuous mode. Needs the render width driven by the zoom scale (re-render with hysteresis, area-capped).
2. **Continuous zoom does not change list layout.** The `graphicsLayer` scale is applied to the whole overlay, not to item sizes. Compose hit-testing follows the layer transform, so taps land, but scroll extent does not grow with the zoom: after zooming in, off-screen parts can only be reached by dragging, and the pan offsets accumulate outside the list's scroll bounds.
3. **Bitmap recycling in composition.** `ContinuousPageView` recycles its bitmap in `onDispose` (`:3274`) and before replacing state (`:3331`). `Image(bitmap.asImageBitmap())` wraps the same `Bitmap` on API 29+, and a still-pending draw can hit a recycled bitmap (`Canvas: trying to use a recycled bitmap`). Prefer letting GC collect, or recycle only from an explicit cache eviction path.
4. **PDF opened on the main thread during composition.** `remember { pdfDocCache.document(...) }` (`:3280`) reads and parses the PDF synchronously; the first composition of a page in a large PDF can jank/ANR. Move it to `produceState`/IO with a placeholder ratio.
5. **Continuous scrolling loads pages into the hidden canvas.** `setCurrentPageIndex` on scroll (`:1216`) fires `LaunchedEffect(currentPageIndex)` (`:352`), which decodes and applies every scrolled page to the hidden `DrawingCanvasView`. Gate that effect on `!isContinuous` and apply only when switching to single mode.

### P2 — memory / OOM

6. **PDF render budget is now 72 MB per background.** `PdfRenderPolicy.MAX_PIXELS = 18_000_000` (72 MB ARGB) and a re-render keeps old + new alive (144 MB). With 6 undo snapshots of a 2160×3056 page (26 MB each ≈ 158 MB) this sits close to the `largeHeap` ceiling; a 256 MB-heap minSdk-21 device will OOM. Suggest 8–12 MPx, hysteresis 1.25–1.35, and/or downscaled undo snapshots.
7. **Overflow layer can be 4096×4096 (67 MB).** `initBackingBitmap` caps both sides at 4096 (`DrawingCanvasView.kt:814-815`), so a 2160×3056 PDF page asks for 4096×4096. Size it relative to the page, not the global cap.
8. **Continuous page bitmaps are heavy for their quality.** ~14.5 MB per 1600-px page, several composed at once. Since 1600 px is not enough for zoom anyway, render at viewport width × zoom with an area cap.

### P3 — data integrity

9. **Backup/restore now carries `-shm`.** The WAL is checkpointed before backup (good), but restoring `touchnotes.db-shm` is unnecessary and can be inconsistent with the restored db; restore `db` + `-wal` only and delete `-shm`. Also consider an integrity/version check after restore.
10. **Debounced save can race a recycled bitmap.** `saveCurrentPageBitmapDirect` does not check `isRecycled`; undo/page switches recycle the backing bitmap. `BitmapUtils.saveBitmapToPng` catches the exception, so the failure is silent (lost stroke) rather than a crash. A defensive copy or `isRecycled` guard closes the race.

### P4 — minor

11. `PdfRenderPolicy.capPxPerPt` KDoc still cites the old 8 MPx budget.
12. `PageTurningSettingsTest` asserts implementation constants (18 MPx, 1.15); behaviour-based assertions age better.
13. PDFs imported before the vector engine (`pdfSourcePath = ""`) remain raster forever — re-import is still the only fix.
14. `state/STATE.md` / `FEATURES.md` do not describe the six commits yet.
15. Six commits are local only (`origin/main` is at `2676e7b`).
